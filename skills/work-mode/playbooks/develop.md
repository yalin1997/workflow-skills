# 開發：從任務到可信任 PR

## 1. 確認任務與現況

把需求變成可觀察的完成條件與不變條件；確認 repo 規則、相關入口、資料形狀、測試方式與必要 CI。只讀相關模組與直接依賴，不先產生全 repo 報告。

依變更需要調整深度：小修補直接列步驟；新功能釐清介面及失敗行為；涉及模組責任、公開 API、schema、併發或系統架構時載入 `work-design`。風險由影響判斷，不由 diff 行數判斷。

## 2. 建立可驗證的起點

- **Bug：** 先以原本入口重現，保存輸入、實際結果與預期差異。能低成本自動化時先加入會失敗的回歸測試；無法重現時標記限制，以可區分假設的證據繼續調查，不宣稱已證實根因。
- **功能／修改：** 先從完成條件列必要案例，再實作；覆蓋主要成功路徑、關鍵失敗與受影響的邊界。外部介面、持久化或多元件協作需要對應整合驗證，不能全以 mock 代替。
- **重構：** 明列要維持的外部行為，以既有測試或特徵化樣本建立基準。純文件、格式等低影響變更不用新增鏡像測試。

Test cases 可直接存在測試名稱／程式與一張簡表，不另造重複的測試規格書。預期結果須有需求、契約或獨立樣本作依據。

## 3. 小步實作

依可驗證單位完成變更，沿用既有測試與結構；不順便升級依賴或重寫無關模組。跨任務介面先固定，再由 Harness 安排隔離或順序；沒有隔離時不要並行修改。

新系統可分成垂直切片：先跑通一條最小端到端流程，再逐步補完整案例及失敗處理。每片可以審查與驗證，不把「寫完各層」當成已完成整條功能。

## 4. 本機驗證

載入 `work-verify`。實際執行專案適用的 unittest、PyBuilder 或既有命令，補對應的行為驗證。命令不由本流程硬編，從 repo 和已核准環境確認。

失敗先查證原因；修復後重跑受影響檢查。不為過測試而削弱斷言，不將環境／依賴問題誤記成產品通過。

## 5. PR、必要 CI、交付

載入 `work-pr`：聚焦檢查 diff，建立或更新 PR，確認雲端必要檢查。CI 失敗時讀相關失敗片段再處理；修改後使相關證據更新到新 revision。

必要驗證及 CI 都通過，才標記「可交人審」。只有本機通過、CI 尚未執行或某個必要案例未驗證時，PR 保持草稿／待驗證並明列阻擋。保留已完成工作，不以完成字樣掩蓋缺口。

終點是人類可審查的 PR 與精簡證據；merge 由人類處理。
