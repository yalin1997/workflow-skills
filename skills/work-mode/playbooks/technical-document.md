# 深度技術 Markdown

1. 確認讀者、要回答的問題、交付檔案及來源範圍。標記文件描述的是「現況」「提案」或兩者差異；深度依需求，不預設限制篇幅。
2. 先建立小範圍來源清單：相關程式符號與 revision、設計決策、測試、PR 或實測資料。重用同任務已確認的資料；不為寫作重新掃描整個 repo。
3. 先交代問題與整體模型，再解釋元件責任、資料／控制流程、重要介面與不變條件、失敗處理、設計取捨、例子及驗證方式。只寫對該主題有用的項目。
4. 技術結論附可追溯來源。現況由程式或實測支持；設計理由若沒有決策紀錄，標記為推測；未實測數字不寫成效能成果。
5. 需要圖時才載入 `drawio.md`；圖和正文共用名稱、邊界與來源。沒有要求圖就不自動擴增交付物。
6. 做一次內容自查：讀者是否能按文件理解／重現、範例與指令是否適用、來源是否支撐結論、現況與提案是否混淆。操作指令只在核准環境驗證；未跑明確註記。
7. 交付 `.md`、必要附件及剩餘問題。文件修改若需納入 repo 審核，按使用者範圍載入 `work-pr`；不自動對外發布。

可用骨架：問題與讀者 → 系統模型 → 深入機制與範例 → 取捨與限制 → 驗證方式 → 來源。這是寫作提示，不是每份文件都必須填滿的表格。
